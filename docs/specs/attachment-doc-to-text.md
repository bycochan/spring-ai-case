# Spec：附件上传支持文档（PDF/Word/TXT）并转换为模型可读文本

状态：本地草稿。搬运到 GitHub Issues 时打 `ready-for-agent` 标签（无需额外 triage）。
背景词汇：见 `CONTEXT.md`（附件 / 文档 / fileId 不可混用）；遵循 ADR 0001（附件体系与 RAG 文档体系分离）。

## Problem Statement

聊天用户想把 PDF、Word、TXT 等文档作为附件随消息发给模型，让模型基于文档内容回答问题。但当前附件上传只接受图片格式，文档直接被拒；即使绕过上传，模型也无法理解二进制文档内容。RAG 的文档上传虽然能解析 PDF/Word，但它会把文件解析、分块、向量化入库且不留原文件，属于知识库检索链路，不适合"随消息附带、保留原文、按 fileId 引用"的附件场景。

## Solution

附件上传扩展为同时接受图片与 PDF/Word/TXT 文档；后端新增一个"附件转文本"方法，把附件字节转换成模型可识别的纯文本。发送消息时，文档附件自动提取文本并拼入用户消息正文，与图片的多模态路径并列；附件失效时的降级策略沿用现状。图片行为、RAG 体系、存储方式均不变。

## User Stories

1. As a 聊天用户，I want 上传 PDF 文件作为附件随消息发送，so that 模型能基于文档内容回答我的问题
2. As a 聊天用户，I want 上传 Word（.docx）文档作为附件，so that 无需手动复制粘贴长文本即可向模型提问
3. As a 聊天用户，I want 上传纯文本（.txt）文件作为附件，so that 快速分享日志、代码片段等文本内容
4. As a 聊天用户，I want 文档附件的内容与我的提问在同一条消息中送达模型，so that 模型按完整上下文作答而不是只看到文件名
5. As a 聊天用户，I want 上传不支持的格式时收到明确的中文错误提示，so that 我知道该换什么格式
6. As a 聊天用户，I want 上传超过大小上限的文档时收到明确提示，so that 我可以压缩或拆分后再发
7. As a 聊天用户，I want 文档解析失败（如损坏文件、无文本层的扫描件 PDF）时得到失败提示而非静默吞掉，so that 我知道模型并没有真正读到内容
8. As a 聊天用户，I want 文档附件与图片一样按 fileId 从会话历史回显引用，so that 多轮对话中附件引用不丢失
9. As a 聊天用户，I want 附件失效（服务重启、被删除）时该条消息降级为占位提示而不是报错中断，so that 历史会话仍可继续
10. As a 聊天用户，I want 文档附件与图片共用"单条消息最多 5 个、单个 10MB"的额度，so that 约束简单可预期
11. As an Agent 创建者，I want 用现有的"图片上传"功能开关一并控制文档附件，so that 不必理解和学习新的开关项
12. As a 开发者，I want 附件转文本只有一个服务方法作为入口，so that 测试面与维护面最小
13. As a 开发者，I want 转换逻辑复用现有 PDF/Word 解析实现而不引入新依赖，so that 构建体积与升级风险不增加
14. As a 开发者，I want 类型/大小校验与其他附件校验一样抛统一的业务校验异常，so that 错误处理路径一致
15. As a 前端开发者，I want 上传接口的请求与响应字段保持不变，so that 现有调用方式无需适配
16. As a 运维者，I want 附件仍只存内存、重启即清，so that 不引入持久化与清理负担

## Implementation Decisions

- **唯一新缝**：在附件服务上新增一个公开方法（如 `extractText`）：输入附件（按 fileId 定位），输出纯文本。这是"附件 → 模型可读文本"的唯一入口，内部委托现有的文档解析服务。
- **解析复用**：PDF/Word 解析沿用现有实现（PDFBox、POI，均已在依赖中，不新增依赖）；文档解析服务扩展支持纯文本类型（.txt / text/plain）。按 MIME 类型与文件名后缀双保险判定格式。
- **上传白名单扩展**：图片四类（JPG/PNG/GIF/WebP）之外新增 application/pdf、Word（.docx）、text/plain。大小上限沿用 10MB，单条消息附件数沿用 5 个，文档与图片共用额度。
- **校验语义不变**：非法格式、超限、附件不存在等继续抛统一的业务校验异常（IllegalArgumentException），控制器层现有的错误包装与响应结构不变。
- **聊天接入**：构建用户消息时，图片附件维持现有 Media 多模态路径；文档附件调用新方法提取文本，以带文件名标注的文本块拼入消息正文。附件缺失/失效、提取失败时沿用现有降级策略（占位提示、跳过该附件），不中断对话。
- **不缓存提取结果**：附件继续只保留原始字节，转换在调模型前按需进行；不新增内存字段、不做持久化，与"重启即清"的生命周期决策一致。
- **不新增功能开关**：Agent 上现有"图片上传"开关的语义扩展为控制全部附件（图片 + 文档），不改 Agent 模型与配置界面结构。
- **体系分离不变（ADR 0001）**：文档附件不做向量化、不产生 documentId，与 RAG 文档体系保持两套链路。
- **词汇表更新**：`CONTEXT.md` 中"附件"条目不再限定"仅接受图片格式"，补充文档附件语义。

## Testing Decisions

- **好测试的标准**：只测外部行为——上传对合法/非法类型与大小的接受与拒绝；转换方法对真实 PDF/Word/TXT 字节产出包含预期内容的文本；聊天链路断言发送给模型的用户消息包含文档文本。不测解析器内部调用细节。
- **测试缝**：全部打在两个既有缝上——附件服务（上传白名单 + 新方法）与对话服务（文档附件拼入消息）。不为解析器单独开测试缝。
- **测试模块**：附件服务测试（新增，服务级）；对话服务测试（扩展现有类，补充文档附件场景：文本进入消息、附件失效降级、开关关闭时拒绝）。
- **先例**：沿用对话服务测试的既有模式——`@SpringBootTest` + 对外部依赖（ChatModel 等）`@MockBean`，附件服务用真实内存 bean 直接构造附件；运行需占位 API key（`mvn test -Dzhipuai-api-key=dummy`）。
- **夹具**：全部在测试内生成——TXT 用内联字符串，PDF/DOCX 用解析同款库（PDFBox/POI）程序化生成最小有效文件，仓库不引入二进制资源。

## Out of Scope

- 前端改造：文件选择器 accept 白名单、文档预览、上传 UI 文案调整（另行处理）。
- Excel/PPT/HTML/Markdown 等其他格式的支持。
- 扫描件/图片型 PDF 的 OCR（无文本层的 PDF 报解析失败提示即可）。
- 老式 .doc 二进制格式的解析增强（按现有实现能力处理，失败即报错）。
- 提取文本的缓存、持久化与向量检索；RAG 文档体系的任何改动。
- 会话历史的持久化。
